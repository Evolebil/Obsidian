## 1. Реляционная модель данных

Реляционная модель данных предложена Э. Коддом в 1970 году. Данные представляются в виде совокупности связанных отношений (таблиц).

### Основные понятия

- Отношение — таблица.
    
- Атрибут — именованный столбец таблицы.
    
- Кортеж — строка таблицы, содержащая значения атрибутов.
    
- Домен — множество допустимых значений атрибута. Например, домен оценки — целые числа от 2 до 5.
    
- Степень отношения — количество атрибутов (столбцов).
    
- Кардинальность отношения — количество кортежей (строк).
    

В СУБД отношению соответствует таблица, атрибуту — столбец, кортежу — строка.

### Свойства реляционной модели

1. Атомарность значений — в каждой ячейке находится одно неделимое значение, а не список.
    
2. Уникальность кортежей — одинаковых строк быть не должно.
    
3. Отсутствие фиксированного порядка строк и столбцов — порядок задаётся явно при выборке данных.
    

Реляционные базы данных позволяют хранить данные в связанных таблицах и объединять их с помощью SQL-запросов.

## 2. Ключи и целостность данных

### 2.1. Первичный ключ (PK — Primary Key)

Первичный ключ — минимальный набор атрибутов, однозначно идентифицирующий каждый кортеж отношения.

Виды первичных ключей:

- Естественный — имеет смысл в предметной области: номер паспорта, СНИЛС, ИНН.
    
- Суррогатный — искусственно генерируемый идентификатор, например `id`, не зависящий от смысла данных.
    

На практике часто предпочитают суррогатные ключи, поскольку естественные значения могут изменяться, содержать ошибки или не всегда быть уникальными.

Требования к первичному ключу:

- уникальность;
    
- обязательность значения — `NULL` запрещён.
    

Это обеспечивает целостность сущностей.

### 2.2. Внешний ключ (FK — Foreign Key)

Внешний ключ — атрибут или набор атрибутов, ссылающийся на первичный ключ другой или той же таблицы.

Пример: столбец `student_id` в таблице оценок ссылается на первичный ключ таблицы студентов.

Внешний ключ обеспечивает ссылочную целостность: нельзя создать ссылку на несуществующую запись.

При удалении записи, на которую ссылаются другие таблицы, СУБД может:

- запретить удаление;
    
- выполнить каскадное удаление связанных записей;
    
- обнулить ссылку, если это допускается настройками.
    

### 2.3. Другие ограничения целостности

- `CHECK` — проверяет соответствие значения заданному условию.
    
- `NOT NULL` — запрещает отсутствие значения.
    
- `PRIMARY KEY` — задаёт первичный ключ.
    
- `FOREIGN KEY` — задаёт внешний ключ.
    

Эти ограничения позволяют поддерживать согласованность данных на уровне СУБД, а не только приложения.

## 3. Избыточность и аномалии данных

Избыточность данных — многократное хранение одних и тех же сведений.

Пример таблицы:

`Заказ(номер, дата, клиент, город, телефон, товар, количество)`

Если клиент Иванов из Казани оформил два заказа, его город и телефон повторяются в обеих строках. При большом количестве заказов данные дублируются многократно.

Избыточность приводит к трём видам аномалий.

### 3.1. Аномалия обновления

При изменении города клиента необходимо изменить все строки с его заказами. Если часть строк не обновить, данные станут противоречивыми.

### 3.2. Аномалия вставки

Нельзя добавить сведения о новом клиенте, пока он не оформил заказ, поскольку информация о клиенте хранится вместе с информацией о заказе.

### 3.3. Аномалия удаления

При удалении последнего заказа клиента вместе с ним теряются все сведения о клиенте.

### Как устранить проблему?

Данные клиента следует хранить один раз в таблице клиентов, а в таблице заказов оставить только ссылку на клиента.

Изменение структуры таблиц по формальным правилам называется нормализацией.

## 4. Нормализация баз данных

Нормализация — последовательное преобразование структуры таблиц для устранения избыточности и аномалий данных.

### 4.1. Первая нормальная форма (1НФ)

Требование: все значения должны быть атомарными, в ячейках не должно быть списков и повторяющихся групп.

Пример нарушения:

|Номер заказа|Товары|
|---|---|
|101|Ручка, бумага, скотч|

Правильное решение — отдельная строка для каждого товара заказа.

Устраняет: списки и повторяющиеся группы в ячейках.

### 4.2. Вторая нормальная форма (2НФ)

Требование: каждый неключевой атрибут должен зависеть от всего составного ключа, а не от его части.

Это требование рассматривается для таблиц, имеющих составной ключ.

Пример:

`Позиция(номер_заказа, код_товара, наименование, количество)`

Составной ключ: `(номер_заказа, код_товара)`.

Наименование товара зависит только от `код_товара`, а не от всего ключа. Поэтому его необходимо вынести в отдельную таблицу товаров.

Пример SQL:

```
CREATE TABLE goods (
    id INT PRIMARY KEY,
    name TEXT
);
```

В таблице позиций остаются ссылка на товар (`goods_id`) и количество.

Устраняет: зависимость неключевых атрибутов от части составного ключа.

### 4.3. Третья нормальная форма (3НФ)

Требование: неключевые атрибуты не должны транзитивно зависеть от первичного ключа через другие неключевые атрибуты.

Транзитивная зависимость — зависимость одного атрибута от ключа через другой атрибут.

Пример:

`Клиент(код_клиента, город, регион)`

Регион определяется городом, а не непосредственно клиентом. Поэтому города и регионы выносятся в отдельную таблицу, а клиент хранит только код города.

Устраняет: транзитивные зависимости между неключевыми атрибутами.

### 4.4. Сравнение нормальных форм

|Нормальная форма|Устраняемая проблема|Решение|
|---|---|---|
|1НФ|Списки и повторяющиеся группы|Отдельная строка на каждый экземпляр|
|2НФ|Зависимость от части составного ключа|Перенос атрибута в отдельную таблицу|
|3НФ|Транзитивные зависимости|Выделение справочников|

Запомнить можно так:

- 1НФ — одно значение в ячейке.
    
- 2НФ — каждый неключевой атрибут зависит от всего ключа.
    
- 3НФ — каждый неключевой атрибут зависит от ключа напрямую.
    

Обычно учётные базы приводят к 3НФ. Иногда применяют денормализацию — намеренное отступление от нормализованной структуры ради повышения скорости выполнения отчётов. Такое решение принимают осознанно, учитывая возможное увеличение избыточности.

## 5. ER-моделирование и переход к таблицам

ER-модель (Entity — Relationship, «сущность — связь») — модель предметной области, используемая при проектировании базы данных до создания таблиц.

### 5.1. Основные понятия

- Сущность — класс объектов предметной области: студент, группа, дисциплина, заказ, товар.
    
- Атрибут — свойство сущности.
    
- Связь — ассоциация между сущностями.
    

### 5.2. Типы связей

- 1:1 (один к одному) — одной записи соответствует не более одной записи другой сущности.
    
- 1:N (один ко многим) — одной записи соответствует несколько записей другой сущности.
    
- M:N (многие ко многим) — нескольким записям одной сущности соответствуют несколько записей другой.
    

### 5.3. Нотации ER-диаграмм

Основные нотации:

- Чена;
    
- IDEF1X;
    
- «вороньи лапки».
    

На диаграмме сущность изображается прямоугольником, атрибуты указываются внутри, а связи отображаются линиями с обозначением кратности.

### 5.4. Преобразование ER-модели в реляционную схему

Основные правила:

1. Сущность → таблица.
    
2. Атрибут → столбец.
    
3. Ключевой атрибут → первичный ключ.
    

Связь 1:N реализуется внешним ключом на стороне «многих».

Пример: одна группа содержит многих студентов. В таблице `students` размещается столбец `group_id`, ссылающийся на группу.

Связь M:N реализуется промежуточной таблицей с двумя внешними ключами.

Пример: студент изучает несколько дисциплин, и каждую дисциплину изучают несколько студентов.

Создаётся таблица:

`enrollments(student_id, discipline_id)`

В неё можно добавить атрибуты самой связи, например оценку и семестр.
