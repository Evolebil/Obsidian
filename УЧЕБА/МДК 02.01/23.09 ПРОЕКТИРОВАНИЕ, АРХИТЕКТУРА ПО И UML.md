## 1. ОСНОВНЫЕ ОПРЕДЕЛЕНИЯ

**Проектирование** — процесс определения архитектуры, компонентов, интерфейсов и данных системы на основе требований. Мост между «что делать» (спецификация) и «как делать» (код).

**Общее (внешнее) проектирование** — определяет крупные части системы: архитектурные слои, подсистемы, интерфейсы между ними, модель данных, выбор СУБД и технологий.

**Детальное (внутреннее) проектирование** — определяет устройство каждого компонента: классы, алгоритмы, структуры данных, сигнатуры функций, схемы БД.

**Архитектура программного обеспечения** — фундаментальная организация системы: её компоненты, их связи и принципы развития. Архитектура определяет самые дорогие в изменении решения, поэтому фиксируется рано и документируется.

**Архитектурный стиль** — устойчивый способ организации системы из типовых частей и связей.

**Слоистая архитектура** — система делится на горизонтальные слои: представление (UI) → бизнес-логика → доступ к данным → база данных. Каждый слой использует только нижележащий.

**Клиент-серверная архитектура** — сервер хранит данные и выполняет основную логику, клиенты запрашивают услуги. Варианты: двухзвенная (клиент — сервер БД) и трёхзвенная (клиент — сервер приложений — сервер БД).

**Монолит** — единое приложение, один процесс.

**Микросервисы** — множество мелких независимых сервисов.

**Модуль** — логически завершённая единица с известным интерфейсом (класс, пакет, сервис). Правило: система строится из модулей, каждый из которых можно разрабатывать, тестировать и заменять независимо.

**Связность (cohesion)** — степень единства ответственности внутри модуля. Хорошо: высокая связность (high cohesion) — модуль делает одну работу. Плохо: класс Utils, куда свалено всё.

**Зацепление (coupling)** — степень взаимозависимости модулей. Хорошо: низкое зацепление (low coupling) — модули общаются через узкие интерфейсы. Плохо: изменение одного модуля ломает десять других.

**Паттерн проектирования** — типовое, проверенное решение повторяющейся задачи проектирования в данном контексте.

**MVC (Model-View-Controller)** — архитектурный паттерн разделения данных, представления и управления: **Модель** хранит данные и бизнес-логику, **Представление** отображает их пользователю, **Контроллер** принимает ввод и управляет моделью и представлением.

**ER-модель (сущность—связь)** — представление данных в виде сущностей, их атрибутов и связей.

**Нормализация** — устранение избыточности и аномалий обновления.

**UML (Unified Modeling Language)** — стандартный графический язык моделирования программных систем.

**Диаграмма вариантов использования (use case)** — диаграмма, показывающая цели пользователей.

**Диаграмма деятельности (activity)** — блок-схема процесса.

**Диаграмма классов (class)** — диаграмма, показывающая статику кода.

**Диаграмма последовательности (sequence)** — диаграмма, показывающая обмен сообщениями между объектами во времени.

## 2. КЛАССИФИКАЦИИ

### 2.1. Результаты этапа проектирования

- документ архитектуры (описание стиля, компонентов, решений с обоснованием);
    
- диаграммы UML: use case, activity, class, sequence;
    
- схема базы данных (ER-модель, нормализованные таблицы);
    
- спецификации интерфейсов модулей и API;
    
- принятые технологические решения (язык, фреймворк, СУБД) с обоснованием.
    

### 2.2. Архитектурные стили

- **Слоистая архитектура** — система делится на горизонтальные слои: представление (UI) → бизнес-логика → доступ к данным → база данных. Каждый слой использует только нижележащий. Плюсы: понятность, замена одного слоя без переписывания других, удобное разделение работ в команде. Минусы: лишние уровни косвенности замедляют простые операции.
    
- **Клиент-серверная архитектура** — сервер хранит данные и выполняет основную логику, клиенты запрашивают услуги. Варианты: двухзвенная (клиент — сервер БД) и трёхзвенная (клиент — сервер приложений — сервер БД). Типичный пример учебного проекта: браузерный клиент на HTML/JS и сервер с REST API.
    
- **Монолит и микросервисы** (см. таблицу ниже).
    
- **Модульная организация** — система строится из модулей, каждый из которых можно разрабатывать, тестировать и заменять независимо.
    

### 2.3. Сравнение монолита и микросервисов

|Критерий|Монолит|Микросервисы|
|---|---|---|
|Структура|Единое приложение, один процесс|Множество мелких независимых сервисов|
|Разработка|Простая стартовая разработка|Сложнее: сеть, контракты API, согласование версий|
|Развёртывание|Одно целое, любой релиз = перевыкладывание всего|Каждый сервис отдельно, независимые релизы|
|Масштабирование|Вся система целиком|Точечно, только нагруженный сервис|
|Отказоустойчивость|Сбой части может уронить всё|Изоляция отказа в одном сервисе|
|Команда|Один-два разработчика|Несколько автономных команд|
|Технологии|Единый стек|Разные стеки под сервис|

**Объяснение:** Микросервисы оправданы при больших нагрузках и крупных командах; для учебного сквозного проекта разумнее модульный монолит: единое приложение с чётко выделенными модулями по слоям.

### 2.4. Принципы SOLID

|Принцип|Суть|
|---|---|
|S — Single Responsibility|У класса одна ответственность и одна причина для изменения|
|O — Open/Closed|Открыт для расширения, закрыт для изменения кода|
|L — Liskov Substitution|Подтип может использоваться вместо базового типа без сюрпризов|
|I — Interface Segregation|Много узких интерфейсов лучше одного «толстого»|
|D — Dependency Inversion|Зависеть от абстракций, а не от конкретных реализаций|

### 2.5. Паттерны проектирования (каталог GoF)

Каталог GoF («банда четырёх») делит паттерны на порождающие, структурные и поведенческие.

- **Singleton (порождающий)** — гарантирует один экземпляр класса и глобальную точку доступа: подключение к БД, конфигурация приложения.
    
- **Factory Method (порождающий)** — определяет интерфейс создания объекта, но выбор конкретного класса делает наследники: создание обработчиков разных типов заявок (сервис, гарантия, возврат).
    
- **Observer (поведенческий)** — объект уведомляет подписанных об изменениях: при смене статуса заявки уведомляются клиент и мастер.
    
- **Strategy (поведенческий)** — семейство взаимозаменяемых алгоритмов за общим интерфейсом: расчёт скидки — фиксированной, процентной, накопительной — выбирается в зависимости от карты клиента.
    

### 2.6. Нормализация

- **1НФ** — все атрибуты атомарны: не «телефоны: дом, раб», а отдельные строки.
    
- **2НФ** — 1НФ плюс каждый неключевой атрибут зависит от всего составного ключа: цена позиции зависит от позиции заказа, а не только от заказа.
    
- **3НФ** — 2НФ плюс неключевые атрибуты не зависят от других неключевых: адрес кофейни хранится в таблице Кофейня, а не дублируется в каждом заказе.
    

**Практическое правило:** для учебного проекта достаточно 3НФ; денормализация допускается осознанно, ради производительности, и фиксируется в документе архитектуры.

### 2.7. Виды диаграмм UML

Диаграммы делятся на структурные (статика: классы, компоненты, развёртывание) и поведенческие (динамика: прецеденты, активность, последовательность, состояния).

**Основные диаграммы:**

- **Диаграмма вариантов использования (use case)** — элементы: акторы (человечки), варианты использования (овалы), границы системы (прямоугольник), связи. Строится так: определить акторов; для каждого актора перечислить его цели как варианты использования; связать общими связями, при необходимости — расширениями (extend) и включением (include). Пример «Трекер командных задач»: актор Участник — «Создать задачу», «Переместить задачу»; актор Руководитель — «Назначить исполнителя», include «Уведомить участника».
    
- **Диаграмма деятельности (activity)** — блок-схема процесса: старт (закрашенный круг), действия (скруглённые прямоугольники), переходы (стрелки), ветвления (ромб), параллельные потоки (жирные полосы синхронизации), финал. Строится: выбрать бизнес-процесс (оформление заказа кофейни), перечислить шаги, определить точки ветвления (оплата наличными или картой), при наличии параллельных работ — добавить полосы.
    
- **Диаграмма классов (class)** — класс изображается прямоугольником с тремя секциями: имя, атрибуты, операции. Видимость: + публичная, - приватная, # защищённая. Связи: ассоциация (линия), агрегация (пустой ромб), композиция (закрашенный ромб), наследование (треугольник у родителя), зависимость (пунктир). Строится: выделить существительные из требований — кандидатов в классы; глаголы — кандидатов в операции; указать множественности (1, 0.._, 1.._). Диаграмма классов — основной результат детального проектирования.
    
- **Диаграмма последовательности (sequence)** — показывает обмен сообщениями между объектами во времени: линии жизни (вертикальные пунктиры), полосы активации (узкие прямоугольники), сообщения (стрелки сверху вниз: синхронные — закрашенная стрелка, ответ — пунктирная). Строится: взять один сценарий use case, перечислить участников слева направо (пользователь, контроллер, сервис, БД), передавать сообщения в порядке потока. Пример: «Оформление брони в музее»: Пользователь → Контроллер: запрос брони; Контроллер → Сервис: создатьБронь(); Сервис → БД: INSERT; БД → Сервис: ok; Сервис → Пользователь: подтверждение.

|---|---|---|
|[draw.io](https://draw.io/) ([diagrams.net](https://diagrams.net/))|Векторный редактор диаграмм|Бесплатный, работает в браузере и офлайн, есть UML-палитра|

## 3. ОБЪЯСНЕНИЯ

**Чем общее проектирование отличается от детального?**  
Общее (внешнее) проектирование определяет крупные части системы: архитектурные слои, подсистемы, интерфейсы между ними, модель данных, выбор СУБД и технологий. Детальное (внутреннее) проектирование определяет устройство каждого компонента: классы, алгоритмы, структуры данных, сигнатуры функций, схемы БД.

**Что такое архитектура ПО и в чём роль архитектора?**  
Архитектура программного обеспечения — фундаментальная организация системы: её компоненты, их связи и принципы развития. Архитектура определяет самые дорогие в изменении решения, поэтому фиксируется рано и документируется. Роль архитектора: принимать и обосновывать архитектурные решения, следить за соблюдением нефункциональных требований (производительность, надёжность, безопасность), удерживать целостность конструкции при доработках. В команде сквозного проекта роль архитектора поочерёдно выполняет один из студентов: он согласовывает структуру модулей и схему БД до начала кодирования.

**Опишите слоистую архитектуру и правило взаимодействия слоёв.**  
Система делится на горизонтальные слои: представление (UI) → бизнес-логика → доступ к данным → база данных. Каждый слой использует только нижележащий. Правило: слой общается только со «своим» соседом; зависимости направлены вниз. Плюсы: понятность, замена одного слоя без переписывания других, удобное разделение работ в команде. Минусы: лишние уровни косвенности замедляют простые операции.

**Сравните монолит и микросервисы: когда монолит — правильный выбор?**  
Микросервисы оправданы при больших нагрузках и крупных командах. Для учебного сквозного проекта разумнее модульный монолит: единое приложение с чётко выделенными модулями по слоям. Монолит проще разрабатывать и отлаживать, он масштабируется целиком, подходит малым и средним проектам.

**Что такое связность и зацепление? Какие значения показателей desirable?**  
Связность (cohesion) — степень единства ответственности внутри модуля. Хорошо: высокая связность (high cohesion) — модуль делает одну работу. Плохо: класс Utils, куда свалено всё. Зацепление (coupling) — степень взаимозависимости модулей. Хорошо: низкое зацепление (low coupling) — модули общаются через узкие интерфейсы. Плохо: изменение одного модуля ломает десять других. Это главные критерии «хорошей архитектуры».

**Расшифруйте SOLID и объясните принцип единственной ответственности.**  
SOLID — это пять принципов объектно-ориентированного проектирования:

- S — Single Responsibility: у класса одна ответственность и одна причина для изменения.
    
- O — Open/Closed: открыт для расширения, закрыт для изменения кода.
    
- L — Liskov Substitution: подтип может использоваться вместо базового типа без сюрпризов.
    
- I — Interface Segregation: много узких интерфейсов лучше одного «толстого».
    
- D — Dependency Inversion: зависеть от абстракций, а не от конкретных реализаций.
    

**Приведите пример применения паттерна Strategy в проекте «Учёт заказов кофейни».**  
Strategy (поведенческий) — семейство взаимозаменяемых алгоритмов за общим интерфейсом: расчёт скидки — фиксированной, процентной, накопительной — выбирается в зависимости от карты клиента.

**Для чего нужен паттерн MVC?**  
MVC (Model-View-Controller) — архитектурный паттерн разделения данных, представления и управления: Модель хранит данные и бизнес-логику, Представление отображает их пользователю, Контроллер принимает ввод и управляет моделью и представлением. MVC лежит в основе Django, Spring MVC, большинства веб-фреймворков; в проекте «Библиотечный сервис» каталог книг — модель, страницы каталога — представление, обработчики запросов — контроллеры.

**Сформулируйте условия 1НФ, 2НФ и 3НФ на примере своей таблицы.**

- 1НФ — все атрибуты атомарны: не «телефоны: дом, раб», а отдельные строки.
    
- 2НФ — 1НФ плюс каждый неключевой атрибут зависит от всего составного ключа: цена позиции зависит от позиции заказа, а не только от заказа.
    
- 3НФ — 2НФ плюс неключевые атрибуты не зависят от других неключевых: адрес кофейни хранится в таблице Кофейня, а не дублируется в каждом заказе.
    

**Перечислите базовые элементы диаграмм use case, activity, class и sequence.**

- **use case:** акторы (человечки), варианты использования (овалы), границы системы (прямоугольник), связи (линии, include, extend).
    
- **activity:** старт (закрашенный круг), действия (скруглённые прямоугольники), переходы (стрелки), ветвления (ромб), параллельные потоки (жирные полосы синхронизации), финал.
    
- **class:** класс (прямоугольник с тремя секциями: имя, атрибуты, операции), видимость (+ публичная, - приватная, # защищённая), связи (ассоциация, агрегация, композиция, наследование, зависимость), множественности.
    
- **sequence:** линии жизни (вертикальные пунктиры), полосы активации (узкие прямоугольники), сообщения (стрелки сверху вниз: синхронные — закрашенная стрелка, ответ — пунктирная).
    

**Почему диаграммы PlantUML удобно хранить в Git-репозитории проекта?**  
PlantUML — текстовая генерация диаграмм: диаграммы описываются кодом, хранятся в Git, легко версионировать. Их можно ревьюить в pull request.

## 6. ВЫВОДЫ (из лекции)

1. Проектирование делится на общее (архитектура, модель данных) и детальное (классы, алгоритмы); его результаты — документ архитектуры, UML-диаграммы и схема БД.
    
2. Архитектура фиксирует фундаментальные решения системы; за её целостность отвечает архитектор, в учебной команде — назначенный студент.
    
3. Основные стили: слоистая, клиент-серверная, модульная; выбор монолита или микросервисов определяется нагрузкой и размером команды.
    
4. Качество конструкции оценивают высокой связностью модулей и низким зацеплением, подкрепляют принципами SOLID.
    
5. Паттерны (Singleton, Factory Method, Observer, Strategy) и MVC — типовые решения повторяющихся задач проектирования.
    
6. Модель данных строится через ER-диаграмму и нормализацию до 3НФ, что устраняет избыточность и аномалии.
    
7. UML даёт стандартный набор диаграмм: use case — цели пользователей, activity — процессы, class — статика кода, sequence — обмен сообщениями.
    
8. Инструменты [draw.io](https://draw.io/), PlantUML, StarUML, Enterprise Architect позволяют вести модели вместе с кодом.
