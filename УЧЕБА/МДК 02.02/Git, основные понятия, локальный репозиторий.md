## ЧАСТЬ 1. От истории СКВ к первому коммиту

> **Проблемный вопрос:** почему команда из десятков разработчиков не теряет ни одной строки кода, хотя все работают одновременно?

### 1.1. Эволюция систем контроля версий

> **СКВ (VCS, Version Control System)** это система, которая отслеживает изменения в коде. Появились в 1970-х.

|Эра|Тип|Примеры|Как устроено|Главный минус|
|---|---|---|---|---|
|**1 (1970–1980-е)**|**Локальные**|RCS, SCCS|История хранится на одном компьютере, следит за правками одного разработчика|Совместная работа невозможна|
|**2 (1990–2000-е)**|**Централизованные**|CVS, Subversion (SVN)|Общая история на центральном сервере, у разработчика только рабочая копия|Без сети нельзя посмотреть историю и закоммитить|
|**3 (с 2005)**|**Распределённые**|Git, Mercurial|**Полная копия истории у каждого участника**|Это современный стандарт|

**Плюсы распределённых СКВ:**

- работа автономна (не нужна сеть);
- ветвление быстрое;
- потеря сервера не означает потерю кода.

> **Про Git:** создан **Линусом Торвальдсом в 2005 году** для разработки **ядра Linux**, после того как отозвали бесплатную лицензию на **BitKeeper**. Нужен был быстрый, надёжный и полностью распределённый инструмент.

> **Статистика:** **>93 %** профессиональных разработчиков используют Git (Stack Overflow Developer Survey 2024). Mercurial и Perforce занимают нишевые сегменты.

### 1.2. Трёхдеревная архитектура Git

> **Ключевое отличие Git от прошлых СКВ:** каждое изменение проходит **три логических дерева**.

|№|Дерево|По-английски|Что это|
|---|---|---|---|
|1|**Рабочая директория**|working directory|Файлы, которые вы редактируете прямо сейчас. Git видит их как изменённые, но **ещё не подготовленные**|
|2|**Индекс**|staging area|Подготовленные к коммиту изменения. Здесь собирается снимок: **что войдёт в следующий коммит**|
|3|**HEAD**|последний коммит|Зафиксированный снимок репозитория и **точка отсчёта** всей дальнейшей истории|

**Схема:**

```
Рабочая директория ──git add──► Индекс ──git commit──► HEAD
```

**Зачем так сложно:** можно подготовить к коммиту **только часть правок**, зафиксировать их, затем подготовить следующие. Получается логически чистая история: **один коммит = одна задача**.

#### Объекты Git

> Всё в истории это объекты Git. Каждый объект идентифицируется **SHA-1-хешем**. Это гарантирует **целостность истории** и делает Git распределённым.

|Объект|Что хранит|
|---|---|
|**blob**|содержимое файла|
|**tree**|структуру каталогов|
|**commit**|снимок с метаданными и ссылкой на родителя|
|**tag**|именованную ссылку|

### 1.3. Базовые команды локального репозитория

> **Шесть команд, которых достаточно для первого коммита.**

|Команда|Что делает|
|---|---|
|`git init`|Превращает текущую папку в репозиторий: появляется скрытый каталог **`.git`** с историей|
|`git status`|«Главный прибор разработчика»: показывает **изменённые, подготовленные и неотслеживаемые** файлы|
|`git add <файл>` / `git add .`|Кладёт изменения **в индекс**, то есть выбирает, что войдёт в коммит (`.` = всё сразу)|
|`git commit -m "сообщение"`|**Фиксирует снимок** с осмысленным сообщением|
|`git log --oneline --graph`|История коммитов: `--oneline` компактно, `--graph` с ветвлениями|
|`git diff`|Показывает, что **изменено, но ещё не подготовлено** к коммиту (рабочая папка против индекса)|

**Типичный порядок работы:**

bash

```bash
git init                          # создать репозиторий
git status                        # что изменено?
git add README.md                 # добавить файл в индекс
git commit -m "feat: добавить README"   # зафиксировать
git log --oneline --graph         # посмотреть историю
```

**Конвенция сообщений коммитов:** префиксы `feat:` (новая функциональность), `fix:` (исправление), `docs:` (документация).

> **Правило:** каждый коммит это снимок проекта с понятным сообщением. **Регулярные небольшие коммиты** привычка профессионала и страховка команды: можно откатиться к любой точке истории.

## ЧАСТЬ 2. Чистый репозиторий и связь с сервером

> Локальный репозиторий удобен для одного человека, но смысл контроля версий раскрывается, когда история хранится **ещё и на сервере**.

### 2.1. .gitignore: что не должно попадать в историю

> **`.gitignore`** это файл в **корне репозитория** со списком шаблонов, которые Git **не отслеживает**.

|Что прятать|Примеры|Почему|
|---|---|---|
|**Секреты**|`.env`, `.env.local`, `secrets.json`|Содержат пароли и токены. Попав в историю, секрет доступен всем, у кого есть репозиторий, **даже после удаления из кода**|
|**Зависимости и артефакты**|`node_modules/`, `vendor/`, `dist/`, `build/`, `target/`|Восстанавливаются одной командой, а это десятки тысяч файлов|
|**Служебные файлы**|`*.log`, `.DS_Store`, `Thumbs.db`, `.idea/`, `.vscode/`|Логи, файлы ОС и настройки редакторов индивидуальны для каждого компьютера и засоряют общую историю|

#### Синтаксис шаблонов

|Шаблон|Что означает|
|---|---|
|`*.log`|все log-файлы в проекте|
|`node_modules/`|весь каталог целиком|
|`/secrets.txt`|только файл **в корне** репозитория|

> ⚠️ **Ловушка:** если файл **уже закоммичен**, добавление в `.gitignore` его **не спрячет**. Нужно:
> 
> 1. удалить файл из индекса: `git rm --cached <файл>`;
> 2. сделать коммит;
> 3. после этого игнорирование заработает.

### 2.2. Удалённые репозитории и SSH-ключи

> **Удалённый репозиторий (remote)** это копия Git-репозитория **на сервере**: GitHub, GitLab, Bitbucket или собственный сервер компании. Платформу выбирает команда или организация.

|Платформа|Что даёт|
|---|---|
|**GitHub**|Публичные и приватные репозитории, pull requests, issues, GitHub Actions, реестры пакетов (бесплатно)|
|**GitLab**|Собственные CI/CD, Pages и Registry|

#### Как настроить доступ по SSH

1. **Сгенерировать пару ключей:**  
    `ssh-keygen -t ed25519 -C "student@example.com"`  
    (работает на Linux, macOS и Windows через Git Bash)
2. **Скопировать публичный ключ:**  
    `cat ~/.ssh/id_ed25519.pub` (файл с расширением `.pub`)
3. **Добавить ключ в аккаунт:** Settings → SSH keys на GitHub или GitLab. После этого `push` и `pull` работают **без ввода пароля**.

#### Команды для работы с сервером

|Команда|Что делает|
|---|---|
|`git clone git@github.com:user/repo.git`|Склонировать существующий репозиторий|
|`git remote add origin git@github.com:user/repo.git`|Привязать удалённый репозиторий к локальному|
|`git push -u origin main`|Отправить локальную ветку на сервер|

> **Про ключи:**
> 
> - **Публичный** ключ (`.pub`) **не секрет**, его можно добавлять на любые платформы.
> - **Приватный** ключ нужно хранить в тайне, он **никогда не покидает ваш компьютер**.

## Контрольные вопросы (с короткими ответами)

| №   | Вопрос                                                              | Краткий ответ                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Чем распределённая СКВ (Git) отличается от централизованной (SVN)?  | В централизованной общая история на сервере, у разработчика только рабочая копия, без сети нельзя смотреть историю и коммитить. В распределённой **у каждого полная копия истории**: работа автономна, ветвление быстрое, потеря сервера не страшна |
| 2   | Трёхдеревная архитектура. Какие команды перемещают изменения?       | Рабочая директория → **индекс** → **HEAD**. Из рабочей директории в индекс: `git add`. Из индекса в HEAD: `git commit`                                                                                                                              |
| 3   | Какие объекты Git существуют? Как идентифицируются?                 | **blob** (содержимое файла), **tree** (структура каталогов), **commit** (снимок + метаданные + родитель), **tag** (именованная ссылка). Идентификация по **SHA-1-хешу**                                                                             |
| 4   | Что такое .gitignore, какие шаблоны?                                | Файл в корне со списком того, что Git не отслеживает. Примеры: `*.log` (все логи), `node_modules/` (каталог целиком), `/secrets.txt` (только в корне)                                                                                               |
| 5   | Зачем SSH-ключ с GitHub? Как сгенерировать?                         | Чтобы `push` и `pull` работали **без ввода пароля**. Генерация: `ssh-keygen -t ed25519 -C "email"`, затем публичный ключ (`.pub`) добавить в Settings → SSH keys                                                                                    |
| 6   | Отличие `git add` от `git commit`?                                  | `add` кладёт изменения **в индекс** (выбирает, что войдёт в коммит). `commit` **фиксирует** снимок из индекса в историю с сообщением                                                                                                                |
| 7   | Что будет, если файл уже закоммичен, а потом добавлен в .gitignore? | **Ничего, файл не спрячется**: Git его уже отслеживает. Сначала `git rm --cached <файл>`, затем коммит, и только потом игнорирование заработает                                                                                                     |
